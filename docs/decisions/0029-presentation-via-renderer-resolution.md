# Draw tools with `registerToolRenderer()`; reach for `registerTool()` only to change behaviour

pi 1.0.1 added `pi.registerToolRenderer()`, which chooses how calls to a tool are drawn — including for tools that are not registered yet — and chains through `next()` to whatever the remaining resolvers and the registered tool would have used. We decided to move all presentation-only customisation onto it, and to restrict `pi.registerTool()` to cases where the tool actually *does* something different. This amends the bash-styling mechanism in ADR 0023 (the package extraction and the visual design of the bash row both stand; only the installation mechanism changes).

Four places in this suite re-register a tool in order to draw it differently, and the codemode one shows what that costs. `packages/ui/src/codemode/tool.ts` re-creates pi's own built-in tool with pi's own options (`appendEntry`, `models`, `getToolNamespace`, `getMode`, `getInlineBudget`) purely so it can attach its renderers — it changes no behaviour. To pull that off it loads `dist/extensions/codemode/tool.js` from the *running CLI*, preserves the built-in `parameters` object identity because MCP and tool-search recognise the codemode tool by schema identity (`extensions/mcp/index.js:405` requires `reachesTools` on whatever is registered), accepts pi's startup notice *"built-in extension `codemode` was not loaded"* as the cost of doing business, and — unnoticed until the 1.2.0 audit — never passes `getToolGuidelines`, so the per-tool prompt guidelines from `ALL_TOOLS`/`describeTool()` silently vanish from the prompt. Four untyped couplings to a private path, one schema identity, one suppressed built-in extension and one degraded system prompt, all in service of a colour. `ui/src/bash/tool.ts:10-18` and `diff/src/tools/{edit,write}.ts:44,24` repeat the pattern at smaller scale, and lose the ability to fall back to native rendering when the user turns our styling off.

**Considered Options**

- **Keep the overrides and patch them forward** — rejected: they work on 1.2.0 today (verified by bundle inspection), so nothing forces the change, but each is a silent-subtractive dependency: when pi adds something to the tool it replaced, our copy wins and the feature disappears without an error. The thinking renderer already drifted this way, losing pi's click-to-toggle `MouseRegion`.
- **Override only codemode, leave bash/edit/write alone** — rejected: an exception that exists because the codemode case is painful is the same as no rule, and the bash override has the same fallback weakness.
- **Ask upstream for per-tool render settings instead of using the extension API** — rejected: `registerToolRenderer` is exactly that request, already shipped and documented, with an official twin in `examples/extensions/built-in-tool-renderer.ts`.

**Consequences**

- **Order is observable, so the migration is two commits per tool: register the renderer first, delete the override second.** pi's resource loader drops a built-in extension whose tool name or command a third-party extension claims (`omitReplacedExtensions`, the mechanism behind ADR 0024), so a state where both exist must be entered deliberately and briefly, not left as a merged condition. After the codemode deletion, the "built-in extension `codemode` was not loaded" notice must be *absent*, `reachesTools` must come from pi's own factory, and MCP tool reachability must be re-checked rather than assumed.
- `next()` makes the styling settings honest for the first time: `bashToolStyling` off means returning `next()`, i.e. pi's native row, instead of re-registering a wrapper to achieve the same thing.
- The thinking renderer is the one patch that survives, because no supported hook exists for a muted Markdown theme on thinking blocks. It is bounded by four conditions: delegate to the original for non-thinking content, keep pi's `MouseRegion` click-to-toggle, honour `outputPad`, and be version-fenced with a visible warning when it declines to apply (never `console.warn` — see the fullscreen-screen decision, ADR 0027). Everything else about thinking — label, collapse, working indicator — moves to `ctx.ui.setHiddenThinkingLabel()`, `setWorkingIndicator()`, and pi's own `hideThinkingBlock` / `ctrl+t`.
- Two capabilities are deliberately **not** adopted. `web_search` / `fetch_content` / `get_search_content` keep direct exposure rather than moving to `codemode`/`deferred`: the token win is real but users would experience it as "web search stopped working", which is a behaviour change, not a compatibility fix. `pi.registerVirtualModel()` (upstream-labelled experimental) and `pi.registerMcpServer()` are out of scope.
- Adopted 1.x surface on our own tools is limited to additive metadata: `outputSchema` + `structuredContent` so codemode callers get structure instead of text, `isError: true` instead of throwing, `exposure: "model-only"` for the orchestrating and asking tools (`subagent`, `ask`), and `annotations` (`destructiveHint` on `sudo_exec`, `openWorldHint` on the web tools) so a third-party permission gate can recognise them.
- In-suite transport moves from `core/bus.ts` to `pi.events`. The Bus existed because pi had no cross-extension bus, and its pre-subscriber queue exists for no other reason; it has no cross-process role — that was always `core/bridge`, which stays as the socket transport. Cost stops flowing over either: the subagent result now carries `usage`, which pi folds into session totals, so `footer`'s cost accumulator and the `COST_UPDATE` event go away and `/session` stops under-reporting subagent spend. The `Bus` glossary entry in `CONTEXT.md` is retired in the ship commit, not the design commit — the glossary describes the code as it stands.

**Implementation note — the `Bus` retirement (2026-10-14, pi 1.2.0).** `packages/core/src/bus.ts` and its `./bus` export are gone; `core/src/events.ts` now holds the six channel constants and their payload types with no transport of its own, and every package moves on the host's own `pi.events`. Measured on real pi 1.2.0 rather than assumed, because this was plumbing and not a rename:

- **Shared between extensions, as the decision claimed — per session, not per process.** Two throwaway extensions loaded into one `pi --mode rpc` run, each holding its *own* `ExtensionAPI` handle (verified: the two `pi` objects differ and so do their `pi.events`), delivered on both edges that matter — a subscription taken at extension load, and one taken from inside a `session_start` handler. What is shared is the bus the resource loader hands to every extension (`DefaultResourceLoader` holds one `createEventBus()` and passes it to each `createExtensionAPI`), and each session replacement builds a fresh loader, so the bus lives for a session rather than the process (`/reload` is the exception: it reuses the loader, so the same bus survives it — and the invalidated runtime's subscriptions are dropped either way, by `createExtensionRuntime().invalidate`). `ask/src/herdr.ts` was already emitting on `pi.events`, as predicted — and reaches only the extensions of the current session.
- **It is not the same contract, in three ways.** (1) It *throws* — "This extension ctx is stale after session replacement or reload." — when a handle is used after its runtime is torn down (measured: an emit deferred past `session_shutdown` threw), where the old bus was a process-lifetime singleton that always answered. So emitting goes through `emitOn()`, which swallows a stale-handle emit: a dropped channel beats a crash inside pi's dispatcher. (2) *A subscriber's throw never reaches the emitter.* `createEventBus()` wraps every handler in its own `try/catch` and prints `Event handler error (<channel>)` with `console.error`. (This note originally claimed the throw was rethrown into the emitter, "as the old bus did"; written as a test — `expect(() => emitOn(bus, …)).toThrow()` — it failed against pi 1.2.0, and a bare `bus.emit` behaves the same. `core/src/events-host-bus.test.ts` pins both halves.) Nothing in the suite breaks — the old bus swallowed listener failures too — but the *destination* changed: the bus logged them through `diag()` to our log file, the host prints them to the console, which is the surface `log-discipline.test.ts` forbids precisely because it smears a fullscreen frame. A listener that cares about its own failures has to report them itself. (3) *Subscriptions are state on the handle, not process state*: every `on()` returns an unsubscribe that must be held, run in `session_shutdown` (registered at top level, per AGENTS.md — not nested in `session_start`), and run again *before* re-subscribing at the next `session_start`. A replacement session re-runs the extension factories once and then — measured live on pi 1.2.0 in RPC mode — hands the fresh instance **two** `session_start` events: `AgentSessionRuntime.finishSessionReplacement` rebinds through `setRebindSession`, and the `new_session` command handler in `modes/rpc/rpc-mode.js` calls `rebindSession()` again. Subscribing per `session_start` without teardown therefore double-delivers immediately: a deliberately naive listener accumulated across restarts and fired six times for two emits by the second generation. `bridge/events.ts` now has a `stop()` that `start()` calls on itself first, and `todo` keys its subscriptions the same way; both behaviours have tests. The host also drops a runtime's subscriptions when it invalidates it (`createExtensionRuntime().invalidate`), which is why no module may keep an "already subscribed" flag across sessions.
- **The pre-subscriber queue is retired for real, not carried over.** No subscriber in the suite listens for something emitted during startup, and pi runs every `session_start` handler before the first `agent_start`/`turn_end`, so a subscription opened at `session_start` is always open in time — verified both directions on real pi: an emit before a listener registers is *not* replayed (a subscriber added 500 ms later received nothing), and a `turn_end` `cost_update` after `session_start` reaches the bridge relay. Nothing in `core/src/events.ts` queues or replays anything: `emitOn` emits and returns. One restart-shaped hazard the queue used to paper over is now handled explicitly: a Client ask reply that settles after the relay restarted carries the generation it was asked on and drops itself instead of decrementing the new session's refcount (`bridge/events.ts`).
- **Floor verified, not assumed.** `EventBus` (`emit(channel, data)` / `on(channel, handler) → unsubscribe`) and `ExtensionAPI.events` are both present in the npm tarball of `@earendil-works/pi-coding-agent@0.85.0`, so `core`'s `>=0.85.0` floor stands and needed no raise. `ask` and `todo` said `>=0.1.0` while now requiring `pi.events` at runtime; both were raised to `>=0.85.0` and their `pi-support` notes updated — that undeclared requirement is exactly what ADR 0026 forbids.

**Implementation note — the take-overs are gone (2026-10-14, pi 1.2.0).** The four take-overs described above are history, not present tense; this note is the record, not an edit to the reasoning. `packages/ui/src/bash/` and `packages/ui/src/codemode/` are now `index.ts` + `renderer.ts` (+ tests), with no `tool.ts` and no `loader.ts`; nothing in the suite imports a path inside pi's `dist/`; `packages/ui/src` contains no `pi.registerTool()` call at all. Both rows come from the one resolver `registerToolRenderers()` installs once per extension load in `packages/ui/src/index.ts`, behind `typeof pi.registerToolRenderer === "function"` and keyed on the tool name, returning `{ ...next(), ...ours }` so whatever else pi's own definition declares survives resolution instead of being dropped by us. `diff` reaches `edit` and `write` the same way (`installEditTool`/`installWriteTool`, behind the same capability check), so pi's own `edit`/`write` stay in place. `pi.registerTool()` now appears only where this ADR means it to — `ask`, `subagent`, `list_agents`, `manage_todo_list`, `sudo_exec`, `web_search`, `fetch_content`, `get_search_content` — tools that exist because of what they *do*, none of whose names is one of pi 1.2.0's built-ins (`bash`, `edit`, `find`, `grep`, `ls`, `powershell`, `read`, `write`), so no registration of ours hides a pi definition. The startup notice accepted above as the cost of the codemode take-over is printed by nothing, because nothing replaces a built-in extension any more. `docs/features/ui.md` carries the shipped description in present tense.
