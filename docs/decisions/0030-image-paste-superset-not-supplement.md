# Keep the paste key by being a superset of pi's clipboard action, not a supplement to it

pi has a native clipboard action, `app.clipboard.pasteImage`, bound to `ctrl+v` (`alt+v` on Windows/WSL), documented as "Paste files on macOS, images, or text from clipboard". `@pi-archimedes/image-paste` binds the same key, and its first-run flow writes `~/.pi/agent/keybindings.json` containing `{ "app.clipboard.pasteImage": [] }` to switch the native action off (`packages/image-paste/src/keybinding-offer.ts:9-24`) — we edit a file in the user's configuration directory to suppress a host feature, then reimplement part of it. We decided to keep both the binding and that suppression, on the condition that our handler becomes a **superset** of what pi's action does on the key: images → attach as image blocks with the multi-image queue and inline preview; file paths → insert at the cursor via `NativeClipboard.getFilePaths?()`, matching pi; otherwise → clipboard text, matching pi. A `suppressNativePaste` setting hands the key back to pi on request.

The audit that prompted this found the asymmetry plainly: pi's action handles three things (files, images, text) and ours handled one, so a user who accepted the first-run offer silently *lost* two behaviours to gain one — and the loss is invisible, because the key still appears to work. The genuinely additive half is real and has no native equivalent: attaching an image to the message rather than writing a path, keeping a queue of several images with `[Image #n]` markers, and rendering a preview. There is nothing to reuse in either direction — pi's dispatcher `readClipboardImage` (`dist/utils/clipboard-image.js`) is not publicly exported, so we cannot delegate to it, and both implementations sit on the same public primitive anyway (`getNativeClipboard()`, ours at `clipboard.ts:74-79`). Given that, the honest framing is that whoever owns the key must implement the whole behaviour of the key, which is a condition we can meet in our own code.

**Considered Options**

- **Hand `ctrl+v` back to pi and rebind ours** (e.g. `ctrl+alt+v`) — the cleanest structure, and the one to revisit if upstream ever makes the clipboard action customisable or exported. Rejected because it changes a headline gesture for existing users in order to fix a gap we can close ourselves, and it leaves the two implementations permanently competing for the same clipboard semantics on adjacent keys.
- **Leave the handler as it is** — rejected: it keeps a silent feature regression that users cannot discover, which is worse than either alternative and is exactly the "the host feature is quietly dead" pattern ADR 0024 was written about.
- **Deprecate the package in favour of pi's native paste** — rejected, and worth contrasting with ADR 0024, where deprecation was right because pi's built-in MCP strictly dominated ours. Here it does not: pi's action writes a temp-file path into the editor (`interactive-mode.js:2515-2525`) and pi's own user-message component renders no images (`user-message.js` contains no `Image`/`showImages` usage), so the queue, the attachment and the preview would simply disappear.
- **Keep the suppression but ask upstream to export the clipboard helper** — rejected as a plan, kept as a wish: it blocks the fix on someone else's release, and if the helper is exported later, collapsing our capture code becomes a small cleanup, not a reversal.

**Consequences**

- We now own the full meaning of `ctrl+v`, including two branches pi already had. If pi adds a third (it added `getFilePaths?()` in the 1.x line), our key silently loses it again — so the parity check is a standing test, not a one-time task, and the floating `pi@latest` job (ADR 0026) is where a change surfaces.
- The generated `keybindings.json` snippet gains `"$schema": "https://pi.dev/schemas/keybindings.schema.json"`. pi 1.2.0 published the configuration schemas, but the keybindings schema is for editors and external validators — pi does not enforce it at startup. `KeybindingsSchema` exists at `dist/core/keybindings-schema.js:13` and nothing in the shipped `dist` imports it. What pi actually does with the file is read it and apply it (`KeybindingsManager.create()`, `dist/core/keybindings.js:304-308`), and it is permissive about what it finds: an entry whose value fails the keybinding-value check is dropped (`keybindings.js:244-253`) and a file that does not parse is discarded whole (`:285-297`) — silently in both cases, with no diagnostic on any path. Startup validation does exist in 1.2.0, but for themes rather than keybindings: `setThemeJsonValidator(validateThemeJson)` (`dist/main.js:452`) validates user theme JSON under `additionalProperties: false` and surfaces failures as startup diagnostics. So a malformed snippet is *not* something the user can see: the entry simply does not bind, and `ctrl+v` keeps pi's native action. That is why the offer asserts the contents of the file it wrote in its own tests (`packages/image-paste/src/keybinding-offer.test.ts`) instead of relying on a host-side warning to tell the user.
- The first-run flow stays, and with it the fact that the suite writes into `~/.pi/agent/`. `docs/features/first-run-keybinding-offer.md` must state plainly what the file is for and that `suppressNativePaste` reverses it, because "why is there a keybindings.json I didn't write?" is a fair question.
- The `1.2.0` fix that expands `~` in `extensions`/`skills`/`prompts`/`themes` settings entries means some users' `!~/…` entries now match where they previously matched nothing, so plugin enablement can shift for them on upgrade independent of anything in this decision.

## Amendment (2026-10-13)

The decision above left `suppressNativePaste` as an abstention rather than a reversal. As specified it meant "skip writing the keybinding snippet", which only ever applies to a file that does not exist yet — gate 4 of the first-run offer refuses to touch a file that is already there. The user who wants the key back is precisely the user who already accepted the offer, and they hold `~/.pi/agent/keybindings.json` containing `{ "app.clipboard.pasteImage": [] }`, which leaves pi's native paste action **unbound**. Declining a future write does nothing to that file. So "hands the key back to pi on request" was a promise the mechanism could not keep, and PR #95's review said so.

**Decided:** turning `archimedes.imagePaste.suppressNativePaste` off must restore pi's native binding, by removing the suite's own unbinding from that file.

**The exception this requires.** Gate 4's rule is "never merge into or rewrite an existing user keybindings file", and restoration is by definition a rewrite of a file that exists. This amends that rule narrowly and deliberately: the extension may rewrite `~/.pi/agent/keybindings.json` only when the file **parses to** the artefact the suite created — a JSON object whose entire content is `app.clipboard.pasteImage` with an empty array as its value, optionally paired with `"$schema": "https://pi.dev/schemas/keybindings.schema.json"`, which is what the offer has written since PR #123 (refusing that pair would leave every install that accepted the offer unable to give the key back without a hand edit; `$schema` counts as ours only with pi's published URL, which keeps the set closed without widening it). The test is on the parsed object, not on the bytes: indentation, key order and whitespace are irrelevant, so this is a content test, not the "byte-shape-identical" wording this amendment originally carried — corrected here on 2026-10-14, because the shipped accept-set (`isSuiteOwnedUnbinding`) has never been byte-exact. Anything else is off-limits: any additional key, a non-empty value for `app.clipboard.pasteImage`, a foreign `$schema`, content that does not parse, a file that cannot be read. In those cases the extension touches nothing and tells the user the one-line edit to make itself — *(corrected in place on 2026-10-14, PR #129: only some of those files hold a one-line edit. A file of foreign keys, a `$schema`-only file, and the three shapes that cannot be inspected hold none, and saying otherwise sent users hunting a line that was not in the file; the message now branches per refusal, and `"pasteImage": []` — pi's pre-rename name for the same action, which `isSuiteOwnedUnbinding` still refuses to rewrite — counts as a file that does hold one.)* The rewrite only ever *removes* that key, leaving `{}`.

*(See the 2026-10-14 amendment below: removing the entry turned out to be half of what "give the key back" means.)*

**Consequences.**

- The extension now writes a user file it did not create, in the sense that it must preserve it. The write therefore uses the same discipline as `writeAtomicPreservingSymlinks` in `packages/core/src/settings-io.ts` — tmp + rename, following an existing symlink so a `keybindings.json` that points elsewhere stays a link instead of becoming a regular file in the agent directory. The offer's own `writeFileSync` + `renameSync` pair does not do this and stays as it is, because it only ever creates a *missing* file.
- It must never touch an unrelated key, in the successful path or any other: the rewrite is "delete our key", not "rewrite the object we think the user meant".
- The restore is idempotent by content — once the file reads `{}` there is nothing to do, so it cannot rewrite a user file on every session start.
- The user is told which case they are in: restored, nothing-to-do, or "this file is yours, here is the line to delete", surfaced through the `core/log` diagnostics path (no `console.*` from a startup path — `docs/features/ui.md`), never a stdout write. *(The third case as worded was itself the bug: corrected in place on 2026-10-14, PR #129 — the warning names an entry only for the refusals that hold one, and `diag` carries the same string the user is shown, not a second wording.)*
- The original decision stands: the superset condition, the first-run offer, and the `$schema` addition are unchanged by this amendment. What changed is only that reversal became something the code does instead of something it declines to do.

## Amendment (2026-10-14): giving the key back takes two halves, and the second one is ours

The 2026-10-13 mechanism shipped, was measured against a real pi, and did not give anyone their key back. Clearing the file is necessary but not sufficient, because we still hold the key:

- `app.clipboard.pasteImage` is not in `RESERVED_KEYBINDINGS_FOR_EXTENSION_CONFLICTS` (`dist/core/extensions/runner.js:9-27`), so `restrictOverride === false` for it, and `ExtensionRunner.getShortcuts` keeps the extension shortcut and records "Extension shortcut conflict: … Using `<ext>`" (`dist/core/extensions/runner.js:467-474`).
- `CustomEditor.handleInput` asks `onExtensionShortcut` first and returns, before its own `app.clipboard.pasteImage` branch (`dist/modes/interactive/components/custom-editor.js:63-70`).

So with the flag off and our shortcut registered, the user got: a clean `keybindings.json`, a recorded intent, one permanent `[Extension issues]` line — and still our handler on `ctrl+v`. (The same two lines falsify the older "both handlers fire on the shared key" story in the READMEs: exactly one handler ever ran, ours.)

**Decided:** while `archimedes.imagePaste.suppressNativePaste` is `false`, image-paste registers **no** paste shortcut at all. `registerImagePaste` reads the same predicate the restore reads (`suiteMayClaimPasteKey`) and skips the whole `registerShortcut` loop — `ctrl+v`, `alt+v` and `ctrl+alt+v` alike — so the restored native binding is the only thing bound to the key.

**Consequences.**

- The trade is now real and is documented where users read it: with the flag off you get pi's paste and lose image-paste's attach/queue/preview on the paste keys. Nothing else in the package is removed — the submit-time marker attachment and the preview renderer stay registered, and there is no other entry point to the paste path to keep (`registerShortcut` was the only one; there is no `/` command for it).
- The gate is read per session, never at module scope: pi caches the extension factory (`dist/core/extensions/loader.js:461-489`) but re-invokes it per session, and the composed suite calls the registration from its own `session_start` handler. Verified live: flipping the setting and pressing `/new` hands the key over with no restart and no file change.
- A file the extension may not rewrite now leaves the key bound to **nobody** until the user deletes the entry — pi's own unbinding is still in it, and we no longer bind it. That is the honest state of a setting that says "don't suppress pi's paste", and the warning says so in the same breath as the one-line fix. *(Corrected in place on 2026-10-14, PR #129: "a file the extension may not rewrite" is not one state. Only a file still holding an unbinding of the paste action — ours under `app.clipboard.pasteImage`, or pi's old name `pasteImage` — leaves the key bound to nobody. A file of foreign keys or a `$schema`-only file never bound it, so pi answers the key on its default; a file pi cannot read or parse is discarded whole (`keybindings.js:285-297`) and every action keeps its default too. The warning names which of the three it is, and asks for a `/reload` only where an edit is actually needed.)*
- The amendment above is corrected in place on its accept-set wording (content-based, `$schema` pair included); nothing else in it changes.

## Amendment (2026-10-15): the first-run offer is conditional on holding the key, too

Both amendments above are about the file that already exists. Neither touched the case where it does not, and there the two halves of this decision contradicted each other: the first-run offer asked to create `~/.pi/agent/keybindings.json` carrying our `app.clipboard.pasteImage` unbinding, and it did so whatever `suppressNativePaste` said, because it was written before that setting existed (PR #125 landed the flag after the offer's gate matrix). On a fresh profile with the hatch open that produced, in one install, the worst of both halves: the user accepted, the unbinding was written while `registerImagePaste` was registering no shortcut, so `ctrl+v` was bound to nobody — pi's action cleared by the file we wrote, our handler deliberately absent — and the next session's restore deleted the file we had just asked permission to create and announced that it had. Two notices about one file, one permission prompt for a file the install had already declined, and a dead key in between. The 2026-10-13 amendment's "the first-run offer refuses to touch a file that is already there" was accurate and beside the point: the offer was not refusing anything.

**Decided:** the offer fires only when `suiteMayClaimPasteKey()` is true — the same predicate `registerImagePaste` and `runNativePasteRestore` already read, with the same strict rule (only the literal `false` counts). Where it is false there is nothing to fix, so the offer does not ask, does not write, and emits no UI text at all. And the skip does **not** consume `keybindingsPromptDone`, exactly as the non-TUI gate does not: the hatch is reversible, and the user who sets the flag back to `true` must still meet the offer in a later session. Consuming the flag there would have made the escape hatch a one-way door for anyone who happened to have it open on their first run.

**The invariant this establishes.** The offer acts only when the predicate is true; `runNativePasteRestore` acts only when it is false (it returns `"suppressed"` the moment the predicate holds). The two flows are mutually exclusive by construction, so *Created ~/.pi/agent/keybindings.json* and *Restored pi's native clipboard paste* can never describe the same file in one install, and neither can undo the other's write. It is stated at both call sites in `packages/image-paste/src/keybinding-offer.ts` and pinned by a test that drives both entry points in the order `meta/src/index.ts` runs them.

**Consequences.**

- The gate is numbered **1b** rather than inserted as gate 2, because the existing gate numbers are cited by name outside the code — `docs/features/first-run-keybinding-offer.md` enumerates them and this document's own 2026-10-13 amendment cites "gate 4". A renumber would have made those citations silently point at the wrong check; the alternative of letting them rot was worse. Its position, immediately after the `enabled` gate, groups the two settings-derived preconditions and puts the skip before the flag read and before the `keybindings.json` stat, so an opted-out profile does no filesystem work for the flow. Neither gate 1's sanctioned ADR 0012 in-package read nor gate 2's "no flag consumed in non-TUI modes" is changed by it.
- Nothing in the decision is reversed: the superset condition, the offer's existence, the consent-based write and the accept-set all stand as they were. What changed is that the offer now reads the setting the rest of the package has been reading since #125 — the omission was an inconsistency, not a trade.
- The default path is untouched: an install that says nothing still gets the offer, still writes the same bytes, and still gets the same single *Created* notice. Measured on a fresh profile before and after the gate, that frame is identical; the only frame that changed is the hatch-open one, which went from two contradictory notices and a spent flag to silence with the offer left armed.
