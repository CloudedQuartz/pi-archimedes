# UI Package (`@pi-archimedes/ui`)

`@pi-archimedes/ui` encapsulates all visual presentation extensions, tool styling, custom editor components, thinking block renderer patches, and startup animations in the Archimedes monorepo.

## Never-do rules (they bind the whole suite, not just this package)

Two rules carry the weight of correctness on a frame-bounded screen, and both are habits this suite used to break. The screen axis itself — what `screenMode()` decides, what the capabilities mean, why a renderer is never stored — lives in [`docs/features/screen-mode.md`](screen-mode.md).

1. **Never decide a colour by parsing an escape string. Ask the theme for a token.** A theme token may be `""`, meaning *terminal default*, and `Theme.getBgAnsi()` renders that as `\x1b[49m` — a **truthy** string, so `getBgAnsi(key) ?? FALLBACK` never reaches the fallback, and a parser that only recognises `38;2;`/`48;2;` hands back a near-black slab instead of "no colour". That is exactly how black borders around the editor on a light terminal got shipped. So: ask for the token (`theme.colors[token]`, `theme.style(…)`), read `theme.appearance` when a light/dark judgement is needed, and treat a terminal-default token as **no colour** — no tint, no derived edge, no substitute token from elsewhere in the palette. `packages/core/src/chrome.ts` is the reference implementation: `tryGetBgAnsi()` → `isTerminalDefault()` → `NO_PANEL_COLOR`, with the hardcoded `PANEL_FALLBACK`/`FALLBACK_FG` constants surviving only for the no-theme-object path (tests, headless).
   *Producers are exempt*: `core/src/color.ts`, `ui`'s logo and `diff/src/ansi/` legitimately **emit** palette codes, and `diff/src/ansi/` keeps a full escape-sequence decoder — the rule is about what a decision is derived from, not about touching ANSI. `diff` stays a standalone package (no `@pi-archimedes/core` dependency), so its parser is a deliberate sibling of `core/src/color.ts`, named as such at `packages/diff/src/ansi/colors.ts`.
2. **Never `console.*` from a render or event path — use `core/log`'s `diag`.** Two independent reasons: on fullscreen screen a stray write lands inside the differential frame and smears the viewport until the next full redraw (on regular screen it scrolled away unseen, which is why the habit survived this long), and inside a subagent child every non-JSON stdout line is discarded by the reader, so a warning vanishes exactly while someone debugs a child run. Developer diagnostics go to `diag(scope, message)` (and `describeError(err)` when the thing caught is an error — a stack belongs in a log file, never in a notification); a message the **user** must act on goes to `ctx.ui.notify`, never to the log, because `diag` is a no-op unless `PI_ARCHIMEDES_LOG` names a file. Both channels are safe on every screen and in a child process.
   The rule is mechanical, not aspirational: `packages/core/src/log-discipline.test.ts` walks every `packages/<name>/src` and `meta/src`, matches **every** `console.<method>(` (including `info`/`debug`/`trace`/`dir`/`table`/`group`/`count`/`clear`), ignores patch sites (`console.log = …`, `typeof console.log`), and its allow-list is `packages/core/src/log.ts` alone — exempt by construction as the sink itself. `packages/diff/src/log.ts` is the standalone package's sibling copy.

## Capabilities

1. **Bash Tool Styling**:
   - **Pi's `bash` tool, drawn by us.** The suite *decorates* pi's own `bash` tool: one resolver installed once per extension load (`pi.registerToolRenderer((toolName, next) => …)` in `packages/ui/src/index.ts`) answers `renderBashCall`/`renderBashResult` when pi asks how a call to `bash` is drawn. Nothing in this package registers `bash`, so pi keeps that tool's executor, description, MCP/tool-search reachability and default-active state — we own only how the row looks. An off setting answers `next()`, which is pi's own row, not a substitute wrapper of ours. (This is ADR 0029; the earlier arrangement — re-registering pi's built-in with our renderers bolted on — is gone.)
   - Header renders the `bash` tool name bold in the theme's `toolTitle` token, with the command preview in `accent` — tokens, never a chosen hue (never-do rule 1).
   - Collapsed view renders status line: `<glyph> <duration> (timeout: <timeout>s)` where the glyph is `▸` in `warning` (running), `✓` in `success`, or `✗` in `error`.
   - Live 1s interval timer updates elapsed duration in-flight. The interval belongs to the row's own renderer state (`ctx.state.interval`) and is cleared when that row's result settles — normally or in error — which is why there is no module-level registry of live rows and nothing to sweep at `session_shutdown`.
   - Expanded view displays `$ <command>`, stdout/stderr output, the spill notice (`[Truncated: showing n of m lines. Full output: <path>]`), an execution duration footer, and the closing `✓ Done` / `✗ Command exited with code n` line.

2. **Codemode Tool Styling** (shipped with PR #66, 2026-10-01; on the renderer-resolution mechanism since ADR 0029):
   - **The same decoration, from the same resolver.** When pi asks how a call to `codemode` is drawn, the resolver answers `renderCodemodeCall`/`renderCodemodeResult`. The suite does not register `codemode`, so pi's own built-in codemode extension stays loaded and stays pi's: the QuickJS executor, the dynamic `prepareLoadout` description with its per-tool prompt guidelines, MCP/tool-search reachability, and `defaultActive: false` activation. Because nothing replaced it, pi prints no "built-in extension was not loaded" notice.
   - What the decoration used to cost, and no longer does: the previous mechanism loaded pi's private `dist/extensions/codemode/tool.js` out of the running CLI, reproduced the built-in `parameters` object identity so the MCP/tool-search extensions still recognised the tool by schema identity, and accepted pi's startup notice as the price. All of that is gone — no file in this package reads a path inside pi's `dist/`, and `packages/ui/src/codemode/` is now just `index.ts` + `renderer.ts` (likewise `packages/ui/src/bash/`).
   - Collapsed view: the `codemode` header (the call row) plus the nested tool calls the script made (last 5, with a `... (n earlier calls, ctrl+o to expand)` hint); a script with no calls shows a single `<glyph> <duration>` line; a failed script appends a `✗ Script failed` marker so a failure is never hidden behind success glyphs. Expanded view: syntax-highlighted script, every nested call (status, args, duration, `models.*` cost, with a `Model calls: $total` line once more than one call reported a cost), output without the executor's `Script completed/failed` header (image blocks show an `[Image: …]` indicator — the renderer is text-only, and the indicator comes from pi-tui's `imageFallback()`), the full-output path when the output was truncated, timing, and the final `✓ Done` / `✗ Script failed` status.
   - **Nothing to decorate, nothing drawn.** The resolver is keyed on the tool name, so a session without a `codemode` tool is never asked about it. And the whole installation sits behind a capability check — `typeof pi.registerToolRenderer === "function"` (the API landed in pi 1.0.1) — so on a host without it this package registers nothing and pi's own rows stand for both `bash` and `codemode`.

3. **Custom Editor**:
   - `HephaestusEditor` wraps Pi's editor component with an animated border spinner (`editorSpinBorder`).
   - Configurable spinner styles, speeds, and quips.
   - **Edge rows are the panel's own colour, not a border.** The editor draws two half-block rows — `▁` above and `▔` below the frame — whose job is to extend the panel's tint flush to the frame, so they are painted in the panel's own colour and vanish into it by construction (`panelEdge` is the winning panel token asked for as a foreground: `theme.colors[userMessageBg]` through pi-tui's foreground emitter, since pi takes a token only in its own slot). Painting them in a border token instead draws a visible rule hugging the text area — the regression that made the panel look bordered. When the theme gives the panel no colour at all (a terminal-default `""` token, or a theme that cannot answer its own token as a foreground) there is no edge colour, and the two rows render as blank spaces rather than block glyphs in the terminal's own foreground; they go blank, they do not disappear, because the frame's height is a layout contract. The `┌──┐` frame itself is a real border and keeps `borderMuted`.
   - **One busy announcement, in one place.** pi's working row writes "Working" above the editor and the border spinner writes its label there too (`editorSpinLabel`'s default is "Working", replaced by a quip for the episode), so with both on screen the word appeared twice. While `editorSpinBorder` is on the row is hidden with pi's own `ctx.ui.setWorkingVisible(false)`, and it is handed back — `setWorkingVisible(true)`, indicator restored with `setWorkingIndicator(undefined)`, so pi's default spinner runs — when the spinner is off. The answer is read from the config on every `session_start`, because pi puts the row back on whenever it replaces the session (`resetExtensionUI()`) and the setting can change between sessions; `session_shutdown` gives it back too (ADR 0014).

4. **Thinking Presentation**:
   - Patches assistant message rendering for collapsible thinking blocks (`autoCollapseThinking`).
   - `thinkingStyle` (Full = full thinking text, Compact = one-line thinking, click to expand) plus code unindentation (`codeUnindent`).
   - `toolStyle` is the **master switch for all Archimedes tool styling**: `Minimal` (default) makes the renderer resolver answer with our rows for `bash` and `codemode` (per-tool `bashToolStyling`/`codemodeToolStyling` toggles fine-tune under it); `Native` makes it answer `next()` for every tool, so pi's own rendering stands. Nothing is registered or unregistered when the session starts — the resolver is installed once per extension load and only its *answer* changes, read from the settings into module state at `session_start` — so `Native` is pi's tool rows, not a differently-installed arrangement of ours. The former `Full` value (auto-expand every tool via a `ToolExecutionComponent` prototype patch) was dropped; `migrateRemovedToolPatch()` restores the true prototype methods if an older version left the patch behind in the same process (upgrade + `/reload`). Legacy `Full`/`Compact` settings normalize to `Minimal` so an upgrade never silently strips styling.

5. **Startup Splash Animation** — **opt-in, and off by default** (`startupSplash`):
   - **pi owns the startup screen unless the user says otherwise.** With `archimedes.ui.startupSplash` off — the default — the package installs no header at all: `session_start` hands the header slot back with `setHeader(undefined)` and pi draws its own startup exactly as it does with no archimedes loaded. Nothing on that path is built and discarded: no header factory is registered, no frame or reveal timer is armed, `ctx.scopedModels` is never read, and pi's `quietStartup` is not even consulted. Everything else in this section is what turning it on (`/archimedes` → Startup Splash, or `"archimedes.ui": { "startupSplash": true }`) gets back.
   - **Both settings, in full.** `startupSplash` is ours and wins outright when it is off; `quietStartup` is pi's own and keeps deciding pi's side of the screen. `readQuietStartup()` reads pi's value from the effective settings — never scraped from its output — and is asked only when the splash is on:

     | `startupSplash`    | `quietStartup` | header slot                     | splash timers |
     | ------------------ | -------------- | ------------------------------- | ------------- |
     | `false` (default)  | `false`        | pi's own header + listing       | none armed    |
     | `false` (default)  | `"header"`     | pi's own header, no listing     | none armed    |
     | `false` (default)  | `true`         | pi's own (empty) header         | none armed    |
     | `true`             | `false`        | the splash, plus `[Models]` when the session scopes any models | frame + reveal |
     | `true`             | `"header"`     | the splash, no `[Models]` row   | frame + reveal |
     | `true`             | `true`         | pi's own (empty) header         | none armed    |

     The last row is deliberate: `startupSplash: true` is an opt in to the splash, not an instruction to overrule pi's own quiet startup, so where pi asked for no header the splash stands down and pi's silence stands. Every row is pinned cell by cell in `startup-splash-gate.test.ts`, which drives the real animation module and counts the timers rather than a mock call.
   - Terminal logo reveal and animation sequences (`animationStyle`), optionally in pi's brand colors (`colorfulLogo`), plus a `[Version]` row stating the running pi version. pi owns its own update check (`pi update`, `/changelog`, `PI_SKIP_VERSION_CHECK`), so the splash makes no network request of its own.
   - **The rows are pi's own listing rows.** The header is installed into pi's header container and pi's startup listing (`[Context]`, `[Skills]`, `[Prompts]`, `[Extensions]`) is the container straight below it, so `[Version]`/`[Models]` are drawn with the recipe `showLoadedResources()` uses: the bracketed name in the theme's `mdHeading` token on its own row, the values in `dim` on the row beneath at a two-space indent, both at column 1, one blank row between sections, and no blank row after the last one — pi brackets the header with `Spacer(1)`s and opens the listing with another, so the gap below the header is pi's to draw. The header used to set its labels in `dim` and its values in `muted`, laid out in padded columns and indented to the logo's centre, which made the intro read as two different documents.
   - **The header is its own content on both screens.** It is not padded to the terminal on regular screen any more — that padding pushed pi's listing down the screen and was the other half of the two-documents look — and on a frame-bounded screen it never was, which is what keeps the editor its share of the viewport (ADR 0027). Nothing about the block depends on the screen, so the header factory no longer asks the renderer which screen it is on and there is no per-screen sizing to go stale when the renderer is swapped.
   - **`quietStartup` is honoured, not scraped** (and only consulted when the splash is on): pi's own setting (`false` / `"header"` / `true`) is read through `readQuietStartup()` from the effective settings, mirroring pi's two predicates — the header is hidden only by `true` (the splash hands `setHeader(undefined)` back to pi, so its silence stands), and the startup *details* are shown only by `false`. Under `"header"` the splash draws the logo and version with no sections. With the splash off, pi applies the same setting to its own startup and this package has no say.
   - **The model scope comes from `ctx.scopedModels`** — the same set `/scoped-models` lists, formatted as pi's own `Model scope:` line does (`id`, plus `:thinkingLevel`) — and appears as a `[Models]` section when details are allowed. It used to be scraped: a `console.log` patch watched for pi printing that line (and swallowed it), and pi's resource components were intercepted out of its container and re-rendered here. Both patches are gone, so pi renders its own listing and the console is nobody's data source.
   - **A finished splash caches its lines** so the text layout does not re-run on every repaint, and it honours `Component.invalidate()` — the hook pi calls on the whole tree whenever the theme changes — by dropping that cache. The cache key is the width it was drawn at, which a theme switch does not change.

## Settings Namespace

All UI settings are stored in `archimedes.ui`. Existing configuration keys are automatically migrated from `archimedes.core` on first run via `migrateCoreToUIConfig()`. `migrateCompactThinkingToStyle()` converts the legacy `compactThinking` key to `thinkingStyle`, and `migrateRemovedToolPatch()` removes the dropped `toolStyle: "Full"` auto-expand wrapper from `ToolExecutionComponent`'s prototype (upgrade + `/reload` in the same process).

`startupSplash` is new enough to have no legacy key, so it is deliberately absent from `UI_CONFIG_KEYS`: there is nothing to migrate, and an absent key reads as the default — off. That is why an existing settings file written before the key existed loses the splash rather than keeping it: the flip was the point.
